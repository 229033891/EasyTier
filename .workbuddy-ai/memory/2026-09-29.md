## 修复顶栏下方 52px 空白带（已完成）
用户截图指出顶栏与页面标题卡之间存在空白。**实测确认**（无头 Chrome 复刻布局测量）：
- 顶栏 `.top-navbar` 是 `position: sticky`，**已占据文档流**，高度 49px。
- 但 `MainPage.vue` 的 `.et-main-content` / `.et-main-content--mgmt` 又加了 `padding-top: calc(3.25rem + safe-area)` = 52px，属于**重复占位**。
- 对比实测：修复前 nav→header 间距 52px，修复后 0px（header_top 49 == navbar_bottom 49，无重叠）。

修复：两处 `padding-top` 改为 `padding-top: env(safe-area-inset-top, 0px)`。

**方法论教训（重要）**：上一轮我曾仅凭 CSS 推演就宣称「布局保持等价」，结果漏掉了这个空白。正确做法是**用无头 Chrome 复刻布局并实测几何值**：
```
chrome --headless=new --disable-gpu --window-size=W,H --virtual-time-budget=4000 --dump-dom file:///...html
```
在页面里 `getBoundingClientRect()` 输出到 pre#result，用 `grep -A 20 'id="result"'` 取值。此法可快速验证 sticky/fixed、flex 分配等布局问题，无需跑起完整应用。

**待确认**：侧栏 `aside` 是 `fixed top-0` + `pt-14`（56px）为 fixed 元素让位，逻辑正确但 56 vs 实测 49px 有 7px 偏差（非本次范围，未改）。
另外 DeviceManagement 有两根节点（v-if spinner + v-else RemoteManagement），建议改布局后在浏览器实看一眼确认无副作用。

## 关键陷阱：`.fixed` vs `.top-navbar` 优先级

- `.fixed{position:fixed}` 在偏移 ~908896
- `.top-navbar{position:sticky}` 在偏移 ~939718（更靠后）
→ **sticky 胜出，顶栏占据文档流**。判断此类冲突必须查构建产物的偏移顺序，不能只看源文件或凭印象。

## 调研：控制台是否记录「两节点间连接 IP:端口 + 延迟」历史（结论：不记录）
用户问控制台有没有连接地址/延迟的历史。逐层查证结论如下，以后要做「历史/趋势」功能可直接复用这份地图：

**数据源都是实时快照**：`PeerRoutePair` = `Route` + `PeerInfo`，其中
- `PeerConnInfo.tunnel`（`common.TunnelInfo`）= `tunnel_type` + `local_addr` / `remote_addr` / `resolved_remote_addr` → **就是 IP:端口**
- `PeerConnStats` = rx/tx bytes、rx/tx packets、`latency_us`
- `PeerConnInfo.loss_rate`、`Route.path_latency`

**easytier-web 后端纯透传**：`restful/network.rs::handle_collect_network_info*` → `client_mgr.handle_collect_network_info` → 直接 RPC 转发给节点。**不落库**。
DB 实体（`src/db/entity/`）只有：users / users_groups / groups / groups_permissions / permissions / tower_sessions / user_running_network_configs / managed_config_revisions —— 没有任何 peer / 延迟表。

**控制台里唯一像「历史」的东西（都在内存，都不持久）**：
1. 事件日志：`easytier/src/instance/runtime_host/event_journal.rs` 的 `EventJournal`，`VecDeque` + `if events.len() > 20 { pop_back() }` → **最近 20 条**，进程重启即丢。事件类型见 `GlobalCtxEvent`（`easytier/src/common/global_ctx.rs`）：`PeerConnAdded/Removed(PeerConnInfo)` 带隧道地址，还有 `ConnectionAccepted/ConnectionError(local url, remote url, ...)`、`Connecting/ConnectError(url)`。前端 `HumanEvent.vue` 只是 `<pre>{{ eventValue }}</pre>` 原样打印 JSON，没结构化。
2. 速率图表：`NetworkChart.vue` `maxDataPoints = 120`，2 秒一个点 ≈ 4 分钟，刷新即清空；**只有速率，没有延迟**。

**唯一持久化延迟历史的地方：`easytier-contrib/easytier-uptime`**（独立服务，`easytier-web` 全仓库零引用）
- `health_records` 表：`status` / `response_time` / `error_message` / `checked_at`，每 5 秒写一条
- `response_time` = 该节点所有 peer conn 里 `stats.latency_us` 的**最小值**（`health_checker.rs`）
- 保留：`CleanupConfig` 默认 30 天 / 每节点最多 70000 条，20 分钟清理一次
- 接口：`GET /api/nodes/{id}/health`、`GET /api/nodes/{id}/health/stats?hours=24`
- **局限：按「共享节点」记录，既不含 IP:端口，也不是「哪两个节点之间」的配对延迟**

**核心的指标系统也不含延迟**：`easytier-core/src/foundation/stats.rs` 的 `StatsManager`，`MetricName` 全是流量/RPC 计数器（无延迟项），内存保留 3 个 epoch、60 秒清理；通过 `get_prometheus_stats` RPC 导出（`easytier-cli stats prometheus`）。web 前端没接这个接口。

**想实现历史功能的三条路（已向用户列出，未开工）**：
- A. 加 `peer_conn_history` 表，采集时落库（instance_id / peer_id / remote_addr / tunnel_type / latency_us / loss_rate / rx / tx / 采集时间）+ 折线图；需定采样间隔与保留策略
- B. 轻量版：事件日志结构化展示（表格化 tunnel 地址/peer/时间）+ 提高保留条数
- C. 给 Prometheus 导出补延迟指标，交给外部 Prometheus 存历史

### 数据量估算（后续要留意）
一行 = 设备×实例×peer×每分钟。单设备 5 实例 × 10 peer ≈ 7.2 万行/天 ≈ **50 万行/7 天**。多设备部署要留意 SQLite 体积；必要时可加「每 key 最大行数」上限或把采样间隔调大。

### 方案A 补充验证（SQL 层已实测通过）
Rust 编译不可用时，用 Python `sqlite3` **直接从源码里正则抽出**迁移 DDL 与 `SERIES_SQL`/`META_SQL`，建内存库造数据跑断言（脚本 `/tmp/phtest/verify_sql.py`，未入库）。已确认：
- 迁移 DDL 可直接执行；`sampled_at / bucket * bucket` 的整数分桶**按绝对 60s 边界对齐**（不是按首条采样对齐）——测试数据必须与 60s 边界对齐，否则每条采样各占一个桶。
- 延迟/丢包 `AVG(CASE WHEN x >= 0 THEN x END)` 正确：整桶都是 -1 时返回 **NULL**（不是 0），前端据此断线；同桶有真实值时正确取均值。
- `MAX(rx_bytes)` 取累计计数器最大值（**不是求和**），跨桶差分算速率与真实速率一致（600B/60s → 10 B/s，120s 桶也是 10 B/s）。
- 计数器重置（连接重建）差分 < 0，前端 `rateSeries` 夹成 0。
- `GROUP BY peer_id` + 裸列 + `MAX(sampled_at)` 确实返回**最近那一行**的 `remote_addr`（SQLite 官方约定），隧道地址变化时取到新地址。
- `EXPLAIN QUERY PLAN` 确认 series 查询走 `idx_peer_conn_history_series` 索引（`SEARCH ... USING INDEX`），只有 GROUP BY 用临时 B-tree。

基于这份已验证的期望值，把 SQL 断言固化成了 Rust 测试：`src/restful/peer_history.rs` 里 `SERIES_SQL`/`META_SQL` 提成模块级常量，新增 3 个 `#[tokio::test]`（`series_buckets_by_peer_and_keeps_missing_latency_null` / `wider_bucket_averages_latency_and_maxes_counters` / `meta_returns_latest_tunnel_address_per_peer`），用 `Db::memory_db()`（会自动跑迁移）。
**坑**：`use sea_orm::ConnectionTrait as _;` 是匿名导入，**不会**通过子模块的 `use super::*` 传下来，测试模块里必须再引一次，否则 `query_all` 找不到方法。
