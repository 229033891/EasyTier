## 移动端按钮布局：一行 1 个 → 一行 3~4 个

用户反馈：mobile 上一行只显示一个按钮，要求一行 3~4 个。

**改的文件**：`easytier-web/frontend-lib/src/components/RemoteManagement.vue`（只改 `@media (max-width: 640px)` 块 + 把原 `@media (max-width: 768px)` 收窄成 `641–768px`）。

**算宽结论**（脚本算的，root 16px；若 root 是 14px 所有 rem 量等比缩放，结论不变）：
- 手机可用宽 ≈ 屏宽 − 45px（`et-main-content` 0.75rem×2 + 卡片 0.6rem×2 + 2px 边框）
- 最长文案 `编辑为文件`（5 汉字）所需宽度：
  - 14px + 带图标 = **103.6px** → 360px 屏一行只能放 2~3 个，且 3 个（101.2px）都差一点放不下
  - 14px + 去图标 = 79.6px
  - 13px + 去图标 = 74.6px（360px 屏 4 列给 74.5px，**只差 0.1px，太贴边**）
  - 12px + 去图标 = **69.6px** → 360px 屏 4 列 75.1px，留 5.5px 余量 ✅
- 所以最终选 **去图标 + 0.75rem(12px) + 内边距 0.3rem + 间距 0.3rem**

**实现要点**：
- 用 `display: grid; grid-template-columns: repeat(auto-fit, minmax(0, 1fr))` 让**每组把整行等分**。`minmax(0, 1fr)` 的下限是 0，所以**永不换行**，每行的按钮数恒等于该组按钮数（配置文件组 3~4 个、网络组 1~2 个），天然不会出现 3+1 的残缺行。

- **踩坑**：`@media (max-width: 640px)` 在前、`@media (max-width: 768px)` 在后，两者在 ≤640px 同时命中，后面的 `min-width: 8.5rem` 会盖掉我的 `min-width: 0` → 网格列宽被撑破。修法是把后者改成 `@media (min-width: 641px) and (max-width: 768px)`。

## 对端历史图表：流量是否记录/展示（用户提问，结论：都已实现，布局保持不变）

用户问「peer 之间的流量数据是否也会记录下来并在延迟图表中展示，是否可行」。逐项确认：

**记录：是。** `peer_conn_history` 每行除 `latency_us`/`loss_rate` 外还有：
- `rx_bytes` / `tx_bytes`：该对端**所有连接**的累计计数器之和（**不是速率**）
- `conn_count`
每 60s 一条。存累计值而不是速率是有意的：连接重建导致计数器归零时只是少一个点，不会把库里的数据写脏；速率由前端对相邻桶差分 `(bytes[i]-bytes[i-1])/(t[i]-t[i-1])` 得到，回退时夹成 0（见 `modules/peerHistory.ts::rateSeries`，有单测覆盖）。

**展示：是，但不在延迟图里 —— 是单独一张「流量」图。** `PeerConnHistoryChart.vue` 当前是上下两张各 160px 的 Chart.js 折线：
1. 「延迟」单线，Y 轴 ms
2. 「流量」双线（上传=tx、下载=rx），Y 轴 B/s（formatBytes 自动 K/M/G）

**问过用户要不要合并成一张双 Y 轴图（省 ~170px 高度），用户选择「保持两张独立图」** → 布局不动。
理由（我的建议也是分开）：延迟 ms（0~300）与流量（0~几 MB/s）量级差几个数量级，双轴叠一起容易误读。

## 调研：后端支持但前端未渲染的配置项（NetworkConfig 字段对照）

用脚本（`.workbuddy-ai/tmp/field_diff2.py`）对比 `easytier-proto/proto/api_manage.proto` 的 `NetworkConfig` 与 `frontend-lib/src/components/Config.vue`：后端共 66 个字段（含 5 个 deprecated），前端渲染 51 个。

**注意脚本判据**：一开始只用 `curNetwork\.(\w+)` 匹配，漏掉了通过 computed 间接绑定的字段（`instance_recv_bps_limit`、`vpn_portal_config` 其实都有 UI）。正确判据是「字段名是否在 Config.vue 里出现过」，但 `advanced_settings` 会因为 i18n key 同名而误判为已渲染。

**未渲染的 13 项分类**：

A. 真缺口、建议补（8 项）
- `networking_method` + `public_server_url`：web 固定用「手动」(peer_urls)，**选不了公共服务器/独立**。而且 locale 里 `networking_method` / `public_server` / `manual` / `standalone` / `public_server_url` 五个文案**已写好但零引用** → 明显是漏接的 UI
- `encryption_algorithm`：只能开关加密（`disable_encryption` 已有），不能选算法（xor/chacha20/aes-gcm/aes-gcm-256/openssl-*）
- `data_compress_algo`：none / zstd，无入口
- `ipv6_public_addr_provider` + `ipv6_public_addr_prefix`：**`ipv6_public_addr_auto`（申请侧）已渲染，提供侧没有入口** → 该功能在 web 上实际不可用

- `prefer_peer_relay`：优先复用已中继到目的地的凭据对端，不再宣告重复直连边

B. 真缺口但偏运维/高级（3 项）
- `secure_mode`（`common.SecureModeConfig`：enabled + X25519 local_private_key/local_public_key）—— 共享节点稳定身份
- `peers`（`NetworkPeerConfig { uri, peer_public_key }`）—— 与 `peer_urls` 并存的另一套，配合 secure_mode 做对端身份校验
- `managed_credentials`（`ManagedCredentialConfig { credential_id, credential_secret, groups, allow_relay, allowed_proxy_cidrs, expiry_unix, reusable }`）—— **RPC 已就绪**（`CredentialManageRpcService` 的 generate/revoke/upsert/list 都在 web 的 rpc 白名单里），但**前端零 UI**（grep `credential` 只命中 generated proto 与 Login.vue 的登录凭据）。体量最大，需要独立面板

C. 不该加到 web（2 项 + 1 项误判）
- `instance_id`：实例 UUID，内部标识
- `credential_file`：节点本地文件路径（"path to credential storage file for persisting generated credentials across restarts (admin nodes)"），web 配置服务器管不到节点文件系统
- `advanced_settings`：proto 里是 UI 状态标记（记住"高级设置"面板展开与否），不是用户配置项

**deprecated 的 5 项无需处理**：`enable_vpn_portal` / `vpn_portal_listen_port` / `vpn_portal_client_network_addr` / `vpn_portal_client_network_len` / `quic_listen_port` 已被 `vpn_portal_config` 取代，而后者**已渲染** ✓
