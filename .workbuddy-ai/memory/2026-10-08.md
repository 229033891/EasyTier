### 2. 修掉一个真实产品 bug：int64 字段导致配置无法保存（BigInt 泄漏）

**症状**：配置里只要有 `managed_credentials` 条目，`toBackendNetworkConfig()` 就抛 `Cannot parse JSON bigint for api.manage.ManagedCredentialConfig#expiry_unix`。

**根因链**：
1. 代码生成用的是 **protobuf-ts**（不是 protobufjs），`int64`/`uint64` 运行时是 **BigInt**（`api_manage.ts` 里只有两个：`instance_recv_bps_limit`、`managed_credentials[].expiry_unix`），而在 **JSON 形状里必须是十进制字符串**。
2. `toBackendNetworkConfig` 走「消息实例 → `prepareNetworkConfigForProtoJson` 展开成普通对象 → 再 `fromJson`」。展开时 BigInt 漏进普通对象，第二次 `fromJson` 就拒绝。
3. `instance_recv_bps_limit` 早就有专门补丁（`normalizeLegacyOptionalUint64` + `normalizeUint64ForInput`），但**嵌套消息里的 int64 没人管**。且 `expiry_unix` 是**非 optional**，protobuf-ts 生成的类会把它初始化成 `0n`，所以**只要 `managed_credentials` 非空就必炸**（不是"设了才炸"）。

**影响面（真实可达）**：`toBackendNetworkConfig` 被 `easytier-web/frontend/src/modules/api.ts`（4 处：保存/校验/启动）和 `easytier-gui/src/composables/backend.ts`（5 处）调用 → 带 managed credentials 的网络在 web 控制台和 GUI 里**保存/启动都会失败**。

**修法**：在 `networkCompat.ts` 的 `dropUnsupportedJsonValues()` 加一行通用转换——`typeof value === 'bigint' → value.toString()`。安全性：该函数只被 `prepareNetworkConfigForProtoJson` 调用，而它的两个调用方（`normalizeNetworkConfig` / `toBackendNetworkConfig`）后面都紧跟 `fromJson`，BigInt 在那里本来就是非法输入（以前直接抛，现在转成它想要的字符串）；且它按树递归，嵌套消息里的 int64 一并覆盖。附带好处：`instance_recv_bps_limit` 从服务器读回是 BigInt 时，以前会被静默丢弃，现在能正确保留。

**回归测试**：`tests/config-ui.spec.ts` 新增 `round-trips int64 fields nested in managed_credentials into backend JSON`（**必须放 vitest**——`test:network-config` 脚本 CI 不跑，`linux.yml:77` 只跑 `test:config-ui`）。

## Win11 安装报错 `Error opening file for writing: %LOCALAPPDATA%\ET\Packet.dll`

**根因（证据链完整）**：
1. `%LOCALAPPDATA%\ET` **就是 NSIS 的 `$INSTDIR`**（Tauri per-user 安装）。
2. `tauri.windows.conf.json` 把 `./wintun.dll`、`./Packet.dll`、`./*.sys` 列为 **resources**；`windows.yml:120` 从 `easytier/third_party/<arch>/` 拷进 `src-tauri/`，安装时落到 `$INSTDIR`。
3. **`Packet.dll` 是 Npcap 的 Packet.dll**（字符串里有 `Insecure.Com LLC`、`npcap\packetWin7\vs14\x64\Release\Packet.pdb`、导出 `PacketOpenAdapter` 等）。
4. **它是 `easytier-gui.exe` 的静态导入**：`pnet_datalink-0.35.0/src/bindings/winpcap.rs:357` 有 `#[link(name = "Packet")]`，而 `easytier/build/main.rs:25` 把 `third_party/<arch>` 加进链接搜索路径；`pnet_datalink` 由 **`faketcp`** feature 引入，而 `faketcp` **在 `default` features 里** → GUI 必然包含。
   → **进程一启动 `Packet.dll` 就被映射，整个进程生命周期内锁定。**
5. 安装钩子原来只对 **`easytier-gui.exe`** 做 rename-aside（`ET_UnlockInstallExe`），**完全没管 DLL/SYS**。所以只要有进程活着：exe 能被改名换新（Windows 允许重命名已映射的映像），**`Packet.dll` 却要原地覆盖 → NSIS 弹这个框**。
6. 谁活着？per-user 安装**不提权** → `sc.exe stop ET-Gui`（SYSTEM 服务）access denied → 服务进程存活；PowerShell 兜底扫描读不到 SYSTEM 进程的 `ExecutablePath` → 被 `-and $$_.ExecutablePath` 过滤掉。**Windows Server 上"基本不报"** 正好对应"那边没装/没跑这个服务或 GUI"。

**已修**：`easytier-gui/src-tauri/windows/installer-hooks.nsh` 新增 `ET_UnlockThirdPartyBinaries` —— 对 `Packet.dll` / `wintun.dll` / `WinDivert64.sys` / `WinDivert32.sys` 逐个 rename-aside（`Rename` + `cmd /c if exist ... move /Y` 兜底 + `Delete /REBOOTOK` 备份），在 `NSIS_HOOK_PREINSTALL` 里 `ET_EnsureGuiStopped` 之后、模板 `File` 拷贝之前执行。刻意**不用 label**（宏若被插两次会因重复 label 编译失败），末尾 `ClearErrors` 免得污染模板后续的 `IfErrors`。

**未验证的部分（已告知用户）**：本机**没有 makensis**，NSIS 改动只能静态检查（`!macro`/`!macroend` 11:11 配平、无 label、指令名对照既有写法），要真正确认得让用户自己打一次安装包。

### 追加：Win10 是否同样有问题 + 卸载必须一并删服务（用户要求）

**① Win10 结论：同样有问题，且同一套修复直接覆盖 Win10。** 逐环节确认过没有一处是 Win11 特有：
- `Packet.dll` 是 exe 的**静态导入** → Windows **加载器**在进程启动时映射它 → 整个进程生命周期锁定。这是加载器行为，Win7/10/11 一样。
- per-user 安装的 `RequestExecutionLevel user`（`INSTALLMODE=currentUser`）→ 不提权 → 停不掉 SYSTEM 服务 → Win10 一样。
- `NSIS` 覆盖被锁文件的报错文案与行为一致。
- **关键旁证**：`.github/workflows/windows.yml` 用 `runs-on: ${{ matrix.OS }}` + `OS: windows-latest`，即 CI 跑在 **Windows Server** 上——正好对应"Server 上基本不报错"，所以 CI 从来复现不了。
- 修复只用了 `Rename` / `Delete /REBOOTOK` / `cmd move`，Win7+ 全支持 → 无需为 Win10 另做改动。

**② 卸载删服务（原来会漏）**：`installer.nsi` 的 `currentUser` 模式是 `RequestExecutionLevel user`（**不提权**），而 `ET-Gui` 服务是 SYSTEM 的 → 原钩子里那两句 `sc.exe delete ET-Gui` / `sc.exe delete easytier-gui` **静默失败（access denied）** → 服务残留、仍指向已删掉的 exe，开机 SCM 报错。已修：

### 追加：安装侧「停服务」提权（用户选了做）

新增 `ET_ElevateServiceStopForInstall`，放在 `NSIS_HOOK_PREINSTALL` 的**最前面**（在 `ET_EnsureGuiStopped` 之前），这样后面的 stop/kill/wait 与文件拷贝都面对一个安静的 `$INSTDIR`：
1. **先判断是否真有服务在跑**（`cmd /c "(sc query ET-Gui | findstr RUNNING || sc query easytier-gui | findstr RUNNING) && exit /b 1 || exit /b 0"`），**没有就不弹 UAC**——避免"普通安装也被弹窗"。
2. 有则在跑 → `ExecShellWait "runas" "$SYSDIR\cmd.exe" '/c sc failure … actions= // & sc config … start= demand & sc stop … & ping -n 4 …'`（两个服务名都处理；`start= demand` 由 `NSIS_HOOK_POSTINSTALL` 恢复成 `auto`）。
3. **UAC 被拒/失败不报错**：`IfErrors` 只打一条 DetailPrint，继续走 `ET_UnlockThirdPartyBinaries` 的 rename-aside 兜底。

**为什么这样设计是安全的（关键）**：本机**没有 NSIS 也没有 Tauri 的 nsh 模板**，无法编译验证，所以刻意规避了两类风险——
- **不引入 LogicLib**（不确定 `currentUser` 模式下是否 include 了它），只用文件里既有的 `StrCmp`/`IfErrors` 写法。
- **标签只放在只展开一次的宏里**：`NSIS_HOOK_PREINSTALL` 全文件只被插入 1 次 → `et_install_svc_stop_done` 在整个文件里只出现 1 次，**无论 NSIS 标签是函数级还是文件级作用域都不会撞**。`ET_DeleteOneService` 仍用参数化 `${SUFFIX}`（`et_svc_done_etgui` / `_legacy`，各自唯一）。
- 静态检查：`!macro`/`!macroend` **14:14 配平**；脚本推演过所有插入点计数（`ET_ElevateServiceStopForInstall` 1 次、`ET_DeleteOneService` 2 次且后缀不同、`ET_EnsureGuiStopped`/`ET_UnlockThirdPartyBinaries`/`ET_UnlockInstallExe` 各 2 次——后者沿用作者原有的 `${__LINE__}` 机制，不是本次引入）。

**关于用户目标「不留 .bak / 不依赖 rename-aside」**：提权成功时文件是自由的，rename-aside 仍会跑但 `.bak` 会被 `Delete` **立即删掉**（不是 `/REBOOTOK` 待重启），所以确实不留残留 ✔；保留它是因为"提权被拒"和"同机其它用户的实例仍持有 DLL"这两种情况仍需兜底。

## 分析：轻微丢包时 RDP 卡顿/断链，同网络下 Tailscale 正常

**主因（代码已验证）：默认配置下隧道优先走 TCP → RDP 变成 TCP-over-TCP。**

证据链（全部有文件/行号）：
1. **默认协议偏好就是 TCP**：`Flags::default()` 里 `default_protocol: "tcp"`（`easytier-core/src/config/toml.rs:100`）；`parse_protocol_preference("")` 也回落 `["tcp"]`（`easytier-core/src/config/protocol_preference.rs:42-44`）。
2. **手动 peer URL 会被"偏好候选"改写，而且偏好候选排在配置 URL 之前**：`preference_candidate_urls()`（`protocol_preference.rs:123-153`）先按偏好生成候选、最后才追加原始 URL；`reconnect()` 逐个试、**首个成功即返回**（`manual/mod.rs:826`）。→ 用户配的 `udp://et.scmec.vip:11010` 会先被改写成 `tcp://et.scmec.vip:11010` 并**优先用 TCP**。这条行为有测试固化（`candidates_follow_preference_then_original`），所以是"有意设计"，但与文档措辞「手动 peer URL 仅在 … 间改写 scheme **降级**」矛盾——**降级应该是失败才降，现在是无条件优先**。
3. **直连（P2P）同样按这个偏好排序**：`direct/mod.rs:475-477` 用 `protocol_preference_sort_key` 排序对端已宣告监听 → 默认下 TCP 排最前 → 打洞成功后的直连也是 TCP。
4. 后果：RDP 自身是 TCP，套在隧道 TCP 里 = **TCP-over-TCP**。轻微丢包时外层 TCP 重传 + 内层 RDP TCP 重传叠加 → RTO 指数退避 → 卡顿；持续丢包直接断链。**Tailscale 只有 WireGuard/UDP，天然不存在这层叠加**，这就是"同网络下它没事"的原因。

**次要放大因素**：
- **MTU 默认 1380**（`toml.rs:103`）vs Tailscale 1280，且**全仓没有 MSS clamp**。underlay 有额外封装（PPPoE/双层 VPN）时 1380+overhead 会超路径 MTU → 分片；丢一个分片整包丢，放大小丢包的影响。
- **`select_conn` 评分把丢包权重设得很高**：`score = 1*RTT + 4*loss + 1*jitter`（`conn_select.rs:97-105`），1% 丢包 ≈ 40ms RTT 的惩罚。而丢包率是用 ping 探测包统计的（`peer_conn_ping.rs` 的 `record_latency(0/1)`），**探测包走 TCP 会被 TCP 自己重传"藏起来"** → 丢包时 TCP conn 反而显得更干净 → 可能把流量**进一步推向 TCP**，自我强化。
- **连接生命周期比 WireGuard 脆弱**：换路/重拨会产生新 conn/session，期间丢包。用户自己的日志里就有 `forward packet error ret=Err(PeerNoConnectionError(...))`、`session id mismatch, clear saved info`、`stop ospf sync session`。Tailscale 的 WireGuard 会话按公钥标识，漫游/换中继都不重建会话。

**排除项**：KCP / QUIC 代理默认关闭（`toml.rs:120/126`，均为 `false`）；全仓没有隧道层分片实现（不存在"分片放大"）。

**确认办法（给用户的诊断）**：
- 日志 grep `manual reconnect start`（`manual/mod.rs:852` 同时打印 `configured_url` 和 `url`）——**两者不同就说明发生了 scheme 改写**。

**修复方向**：
- 短期（配置层，不改代码）：`default_protocol = "udp"` + 只保留 `udp://` peer；或改用 **`wg://`**（`easytier/src/tunnel/wireguard.rs` 是 `boringtun` 真 WireGuard，且 `wg` **不可被 scheme 改写**，最接近 Tailscale）；MTU 降到 1280。
