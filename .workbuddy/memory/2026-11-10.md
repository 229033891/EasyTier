## CI：ET Linux #169 耗时 4h42m 的根因与修复

**根因**：不是编译慢。`build-gui` 与 `build-web-embed` 卡在 `prepare-build` 的
`apt-get update`（`azure.archive.ubuntu.com` 半开连接，日志连续 `Ign:` 后零输出 4h41m，
直到 workflow_dispatch 手动取消）。同一次运行的 `build`（musl 无头）跑同一步骤仅 10.5s，
编译 9m28s。run id 42762937112。

**已改**：
- `.github/actions/prepare-build/action.yml`：Linux apt 步骤加 mirror 回退官方 HTTPS、
  `Acquire::ForceIPv4`、`http/https Timeout=15`、`Retries=3`、`sudo timeout 300/600` 兜底。
  注意 **composite action 的 step 不支持 `timeout-minutes`**，只能用命令级 timeout。
- `.github/workflows/linux.yml`：build_web 20 / build 45 / build-web-embed 45 / build-gui 90
  的 job 级 `timeout-minutes`。
- `docs/ops/ci-failure-log.md`：§3 增检查项、§5 增 2026-11-10 条目。

**遗留待决策**（未处理）：
1. sccache 对 Rust 零命中（`Rust cache_hits=0` / `misses=462` / `cache_write_errors=20`，
   GHA cache 10GB 硬顶）。要么确认 key 稳定性，要么改 `cache-targets: "true"` 走
   `Swatinem/rust-cache` 缓存 target。
2. `releases/**` 仍走 `Cargo.toml` 的 `lto=true` + `codegen-units=1`；建议 CGU 调 4
   （体积涨 <2%，省 20–30%），需用户拍板（发版质量决策）。
3. `build-web-embed` 的 `needs: build_web` 可合并，省 4.5min 串行 + artifact 往返。
   `ET-web-dashboard` 只是中间产物，被 release.yml 排除，合并安全。
4. 长期：预构建 ghcr 镜像（mold/musl-tools/gtk/webkit/protoc/rust）彻底摆脱 apt 抖动。

**排查经验**：看 CI 慢必须先看**步骤级** `started_at → completed_at`，job 总时长会把
`Prepare build environment` 里的 apt/protoc/rust/pnpm 全糊成一坨，极易误判成编译慢。

## 第二轮（同日）：补强 + 三项遗留落地

**apt 卡死的确切机制**（查 GitHub community #205360、conda PR #16895、多个同类仓库后确认）：
1. `/etc/apt/apt-mirrors.txt` 是**优先级列表，Azure 排第一**；Azure 不可达时 `Ign:` 后 failover
   到公网 `archive.ubuntu.com`，而公网 archive 未为该 fleet provision，传输会停在索引文件中途。
   多个上游项目都停在同一个 `noble-security InRelease [126 kB]` —— 高度可复现的 pattern。
2. **决定性**：`Acquire::http::Timeout` 默认 120s，且是 **idle timeout**。连接开着、偶尔
   trickle 几个字节就永不触发 → apt 既不报错也不退出。
3. runner 有 AAAA 记录但 IPv6 路由不通，`connect()` 先卡 IPv6。
4. 裸命令 + composite action 不支持 `timeout-minutes` → 无人终止。

**追加改动**：
- apt 防护升级到四层：mirror 替换（`apt-mirrors.txt` + `sources.list` + `sources.list.d/*`
  全覆盖，含 `ports.ubuntu.com`）、`ForceIPv4`、idle 超时 20s、`timeout --kill-after=30 300`。
  用 bash 数组 `APT_OPTS=(...)` + `"${APT_OPTS[@]}"`，别用字符串靠 word splitting。
  实测 `--kill-after`：忽略 TERM 的进程 1s 后被 SIGKILL（退出码 137）。
- linux.yml：删除 `build_web` job，前端 dist 并入 `build-web-embed`（`prepare-pnpm` 传
  `setup-protoc: 'false'`，因为 prepare-build 已装 protoc）。省 4m33s 串行 + artifact 往返。
  `core-result` 的 needs 同步更新。
- linux.yml：`releases/**` 的 `CARGO_PROFILE_RELEASE_CODEGEN_UNITS` 1 → 4（fat LTO 保留）。
- windows.yml：全部 job 补 timeout（30/150/120/120/10）。

**重要更正**：fork 上 ET Linux 此前*只跑过 #169 一次*（`gh api` 统计：ET Linux n=1）。
所以 `Rust cache_hits=0` 是首次冷启动的必然结果，**不是 sccache 失效**。上一轮把它列为
"第二真问题"是过度解读。等第二次运行看命中率再决定。`cache_writes=780` 说明已写入。

**pre_job 故意不加 timeout**：只跑 skip-duplicate（几十秒），且 `concurrency:
cancel-in-progress` 已覆盖，加了是噪声。

**工具经验**：本机无 PyYAML（pip 无源），但 `node_modules/.pnpm/yaml@2.8.1` 可 `require`
解析 workflow，比肉眼看缩进可靠。`git status` 显示改动已被自动 staged，看 diff 要用
`--cached`；memory 文件记得 `git restore --staged` 掉（AGENTS.md 要求）。

## 第三轮：从「缓解」走到「根治」

**关键事实核查**（查 actions/runner-images Ubuntu2404-Readme.md）：
ubuntu-24.04 runner **预装** gcc/g++/make/dpkg-dev（即 build-essential 核心），
但 **mold / musl-tools / libwebkit2gtk-4.1-dev / libgtk-3-dev / libappindicator3-dev /
librsvg2-dev / libxdo-dev / protobuf-compiler / xdg-utils 全部没有**。
所以不能简单删掉 apt 步骤。

**根治思路**：卡死只发生在 `apt-get update`（拉 20+ 索引文件，每个都是一次可能 stall
的连接）；`apt-get install` 只下 2–3 个 .deb。runner 自带 `/var/lib/apt/lists`，
因此**先直接 install，成功就零索引请求，失败（索引不足）才回退有界 update**。
注意 `apt-get install` 对已装包会直接返回 0 且不联网。

**已实施**：
- `prepare-build` 的 Install dependencies / Install GUI deps 都改为「快路径 install →
  失败才 update」的两段式。
- 防护写进 `/etc/apt/apt.conf.d/99-et-ci-failfast`（ForceIPv4 / Retries=3 /
  http(s)::Timeout=20），覆盖**第三方 action 内部自己跑的 apt**，不再只保护显式命令。
- 保留 mirror 替换 + `timeout --kill-after=30` 作为兜底。

**为什么不 pin 镜像**：查到的实证是——Azure 挂的时候公网 archive 也照挂（本项目与
conda/unsloth 都停在同一个 `noble-security InRelease [126 kB]`），pin 单一源不解决问题。
mirrorlist failover 机制本身是对的，缺的只是「允许它放弃」。

**仍未做（终极方案）**：ghcr.io 预构建镜像 + `container:`，构建期完全无 apt。

**验证手段**：heredoc 经 YAML 剥离缩进后要确认 `EOF` 顶格（用 node 导出 run 文本逐行看）；
分支逻辑用 stub 返回 rc=0/100 模拟 apt 成功/索引缺失两条路径。

- `linux.yml` 三个构建 job 加 `container:`，由仓库变量 `ET_CI_IMAGE` 控制。

**关键技巧**：`jobs.<id>.container` 只允许 `github/needs/strategy/matrix/vars/inputs`
上下文，`secrets` **只能**出现在 `container.credentials`。要让 container 可选，
必须整个对象走一个表达式（`{"image":null}` = 不用容器）：

    container: >-
      ${{ (vars.ET_CI_IMAGE != '' && fromJSON(format('{{"image":"{0}","credentials":{{"username":"{1}","password":"{2}"}}}}', vars.ET_CI_IMAGE, github.actor, github.token))) || fromJSON('{"image":null}') }}

`github.token` 在 container 层可用，所以私有包也能拉；变量为空 → 一键回退普通 runner。
format 里字面 `{`/`}` 必须写成 `{{`/`}}`，本地用 python 模拟 format 校验过渲染结果是合法 JSON。

**验证**：三个分支（无哨兵 / 有哨兵齐全 / 缺工具）用桩 PATH 实测，退出码 0/0/1 符合预期；
全部 YAML 用 `node_modules/.pnpm/yaml@2.8.1` 解析通过；所有内嵌 run 段 `bash -n` 通过。

## 第六轮：真机验证（分支 ci/verify-et-image）

三个此前"只有跑一次才知道"的问题全部有了答案：

| 问题 | 结论 |
|---|---|
| `container: {"image":null}` 是否被接受 | **可以**。4 个 job 正常创建，无 `Initialize containers` 步骤，等价普通 runner |
| 镜像能否构建 | **可以**。ci-image.yml 一次过，自检输出 `ci image ok`，`libprotoc 35.1` |
| 容器内跑构建 | **可以**。三个 artifact 全部产出（gui 20MB / headless 12MB / web 10MB） |

**实测耗时**：#169 4h42m（cancel）→ 42802980322 普通 runner **24m03s** →
42812330906 容器 **16m35s**。`Prepare build environment`：build 10.5s→75s→**4s**；
build-gui 4h41m→5m44s→4m34s（余下是 pnpm 前端构建真实工作量）。容器初始化 31–40s。

**两个容器专属陷阱**（普通 runner 上完全正常，只在 `container:` 下爆）：

1. `hashFiles()` 在 composite action 的 **post 阶段**必失败：
   `hashFiles('**/pnpm-lock.yaml') failed. Fail to hash files under directory '/home/runner/work/<repo>/<repo>'`。
   post 阶段 runner 重新求值各 step inputs，glob 按宿主机路径解析。
   **迷惑点**：所有构建步骤成功、artifact 也上传，job 只因清理步骤变红。
   解法：hash 算进 `$GITHUB_ENV`，post 只读 env（`env.STORE_PATH` 在 post 可用即证明可行）。
2. 容器内 **git 返回 128**：`fatal: detected dubious ownership`。runner 把 `safe.directory`
   只写进临时 HOME（`/__w/_temp/<uuid>`），后续步骤用 `/github/home`。
   **第一版用 `git ls-files` 算指纹就是这么翻车的**，改用 `find` + `sha256sum` 纯文件哈希。

**教训**：往容器化路径放 composite action 前，先 `grep hashFiles` 和 `grep 'git '`。
另外排查"job 红但产物齐全"时，第一件事是看**哪个 step** 失败——往往是 post/cleanup。

**变量**：已在仓库写入 `ET_CI_IMAGE=ghcr.io/229033891/easytier-ci:latest`（repo 级）。
删除即回退普通 runner，无需改代码。

**日志获取技巧**：blob 存储偶发 502 时 `gh api .../jobs/<id>/logs` 会失败，
改用 `gh run view --job <id> --log`（走不同端点）能取到。

**第三个容器坑（重要）**：`cargo nextest archive` 把**容器绝对路径**
`/__w/<repo>/<repo>` 写进 tests.tar.zst，下游普通 runner 是
`/home/runner/work/<repo>/<repo>`，直接报
`workspace root manifest at /__w/.../Cargo.toml does not exist`。
解法：`--workspace-remap "$GITHUB_WORKSPACE"`（非容器模式下是空操作，一份命令
覆盖两种模式）。已写进 ci-failure-log §3 检查清单。

**Dockerfile 补充**：`rustup component add rustfmt clippy` + 加 `wasm32-wasip1`
target（check-wasi 用）。改 Dockerfile 会触发镜像重建，约 13 min（层缓存失效）。

**验证结果**：ET Test run 42827341303 全绿（含 test_matrix 三个分片）；
ET Linux 16m35s；ET Windows 38m01s。

**剩余可选项**：`check-fmt` 与 `bench-routing` 仍未容器化（理由见上）；
`test.yml` 首次冷跑 check-hack 22m42s 偏长，缓存热了应会下降，值得再观察一次。

openwrt.yml 容器化评估（结论：不加）。build-openwrt 用 openwrt/gh-action-sdk@main，
该 action 内部是 docker/build-push-action + `docker run -v <FEED_DIR>:/feed`，
给 job 加 container 会变成容器套容器：无 docker socket 直接失败；强挂 socket 时
容器内 /__w/... 路径在宿主 daemon 不存在，/feed 挂成空目录。且 SDK 镜像本身已是
预装环境，容器化无意义。build-bins 可加但收益极低（仅 releases/** 触发）。
已补 job 级超时：build-bins 45min / build-openwrt 30min，run 42841597857 实测
全绿：build-bins 27m48s（Prepare 3m57s、Build 22m54s），build-openwrt 15m56s，
产物 ET-openwrt-bins 20MB + ET-openwrt-x86_64-apk 20MB。
注意 build-bins 不套 linux 的 thin/16 覆盖是有意的：openwrt 产物要 UPX 进路由器，
走 Cargo.toml 的 fat LTO + CGU=1 保体积，代价就是 Build 22m54s。
