## 压测"丢包抖动"根因与修复（11:00-11:30）

### 根因（三层，必须分开说）
1. **真实丢包 = 上行链路饱和（外部，不归 EasyTier）**：`.20` 16 路时 ICMP 丢 22.6%、`.10` 4 路时 p99 663ms。本机 `tunnel_buffer_full=0`、网卡 discard/error 全 0、`data_plane_no_dst_peer_drops` 未增长 ⇒ 丢在离开本机之后。每条隧道有硬顶：`.20` 1.08MB/s（2/4/16 路都一样）、`.10` 0.46→0.31MB/s。
2. **误判（代码缺陷，已修）**：探测把"预算内没回答"当"丢包"。`fast_probe_timeout = clamp(3×EWMA RTT, 300ms, 2s)`，而**超时不产生 RTT 样本** ⇒ EWMA 学不到后起的队列 ⇒ 预算钉死 300ms ⇒ 每轮必 miss。实测 `rtt_us=6008` → 300ms 预算、真实排队 663ms，`misses=3` 发布 100% loss 10s，剔边 4s；同期业务 103/103 成功、rx_bytes 全程在涨。
3. **保活补不上**：`PingIntervalController` 空闲退避 `1<<backoff_idx`，`max_backoff_idx=5` ⇒ 最长 32s 一次，探测决策的 ~2s 内 `roundtrip_epoch` 常常不变。

### 修复
- `peer_conn_ping.rs`：每轮探测前后采 `throughput_stats.rx_bytes()`，本轮有字节到达 → `path_carried_data=true`，与 keepalive epoch **同级**折算为"本轮被证明存活"（`roundtrip_proven = epoch_advanced || path_carried_data`）。
- 判定语义由"是否按时回答"改为"是否还在交付"；真黑洞时 rx 同步停止，**3 轮判死 / 9 轮剔边时间完全不变**。
- 阈值、间隔、预算区间、sustained 门槛一律未动 ⇒ "最坏检测 ≈1.9s" 与传播链路的 10s/22s 结论不变。
- 新增测试：`a_conn_delivering_bytes_is_never_published_as_lost`、`delivery_alone_clears_a_published_degradation`；5 处旧调用补 `false` 参数保持原语义。
- 文档 `docs/roadmap/live-next-hop.md` 新增"2026-11-08 实测修正：超时≠丢失"小节，并改判死条件表格。

## 探测判定重构（企业级收紧，未提交/未 push）

用户要求"按企业级标准修改"，针对上一轮 `path_carried_data` 修复的三个缺陷重写。

### 改动（仅 `peer_conn_ping.rs` + 文档）
1. **三值→四值判定**：新增 `enum RoundOutcome { Miss, Inconclusive, DeliveryOnly, Proven }`，
   取代 `roundtrip_proven = epoch_advanced || path_carried_data` 的布尔合并。
   - `Proven`（pong/echo）：misses=0, hits+1
   - `DeliveryOnly`（超时但有入向字节且预算短）：misses=0，**hits 不动**
   - `Inconclusive`（LocalCongestion，ping 没出本机）：两个计数器都**不动**（保留原有测试语义）
   - `Miss`：misses+1, hits=0
2. **`DeliveryEvidence { carried_data, budget }`** 取代裸 bool，`excuses_a_timeout()` 带预算门限。
3. **预算自适应（治本）**：`fast_probe` 内维护 `budget_floor`，`DeliveryOnly` 翻倍（上限 2s）、
   `Proven` 减半（下限 300ms）。新常量 `FAST_PROBE_EXCUSE_MAX_BUDGET = 1200ms`——
   预算爬到该值后入向投递不再豁免超时（单向故障出口）。
4. **修 LivenessEcho 双计数**：旧代码一轮可 +2 hit，使恢复从 3 轮缩到 2 轮。
5. 日志加 `budget_ms` / `budget_floor_ms` / `carried_data` 三个字段，便于现场区分真黑洞与单向死。

### 设计要点（为什么不能只是 OR 进 roundtrip_proven）
本机每 333ms 会收到**对端 pinger 的探测 ping**，本身计入 `rx_bytes` ⇒ "本轮有字节"在对端探测循环
活着时几乎恒真。单向故障下本机判活、对端判本机死，两边相反，流量持续进死路且不触发重路由。

- 因此把纯逻辑**逐字**抽到 `target/tmp/probecheck` 独立 crate 真实编译并跑测试：**12 passed**，

## 探测降级日志加诊断字段（判定逻辑不变）

用户问"转发场景 carried_data 恒 false 是否需要优化"。结论：**判定不能改**，只加观测。

### 为什么不能用 tx 判活
对端变黑洞时本机 `tx_bytes` 照样增长（写本地 socket buffer 成功，直到缓冲满），
用 tx 豁免超时 = 永不判死，流量持续打向死路，比"偶尔剔边"严重得多。
relay 场景其实不缺证据：pong 本身就是 rx，探测成功即 `Proven`，走不到 `carried_data` 分支。
本机出口满已由 `try_send` → `BufferFull` → `LocalCongestion`(Inconclusive) 覆盖（peer_conn_ping.rs:617）。

### 改动（4 文件，92+/14-）
1. `tunnel/stats.rs`：`Throughput` 新增 `egress_drops: AtomicU64` + `egress_drops()` / `record_egress_drop()`，
   Clone/Default 同步。放在 Throughput 而非 fq 内部，是因为判定侧需要看见它。
2. `peers/conn/egress_fq.rs`：`EgressFairQueue` 新增 `throughput: Option<Arc<Throughput>>`，
   `new()` 保持零参（5 处测试不动），新增 `with_throughput()` builder 注入；
   `note_buffer_full` 同时 `record_egress_drop()`。
3. `peers/conn/peer_conn.rs`：构造 fq 时 `.with_throughput(throughput.clone())`。
4. `peers/conn/peer_conn_ping.rs`：
   - `DeliveryEvidence` 的 `carried_data: bool` 改为 `rx_delta: u64`（新增 `carried_data()` 方法），
     并加 `tx_delta` / `egress_drops`，均为**观测字段，不参与判定**。
   - 每轮前采 `tx_bytes` / `egress_drops`，与 rx 一起算增量。
   - `publishing degraded loss` 与 `degradation sustained` 两条 warn 输出
     `rx_delta` / `tx_delta` / `egress_drops`，并在注释里写明四种组合的含义：
     `rx=0,tx=0,drops=0` 真黑洞；`rx=0,tx>0,drops=0` 灌黑洞；`rx>0` 预算不足；`drops>0` 本机出口饱和。

## 复核轮（同日晚）：棘轮失效 + 三处修正

### 致命缺陷：`DeliveryExcuse` 整套机制是死代码
`DeliveryEvidence::excuses_a_timeout(&self, excuse: DeliveryExcuse)` 收了 `excuse` 却**没读它**，
判定仍是 `carried_data && budget < CEILING` —— 与上一版逐字等价。编译器直接报
`unused variable: excuse`，但上一轮记录的"21 passed"里没有一条能发现它。

**反证实验**（把 `!excuse.spent` 换成 `true` 复现旧行为）：
`a_one_way_outage_is_published_even_though_the_floor_falls_back` → FAILED
（"a one-way outage must be published within the documented window, not excused forever"）。
即单向故障永不发布降级，流量持续打进洞、路由永不改道。

首次 `Proven` 发生在第 3 轮（1200ms 预算覆盖 663ms 队列），此后 `floor` 在 600/1200 之间振荡；
断言 `floor >= queue` 只是**因为循环跑了 30 轮（偶数）**才成立，改成 29 轮就红。

### 三处修正
1. `excuses_a_timeout`：`carried_data() && !excuse.spent && budget < CEILING`（棘轮真正生效）。
2. 棘轮只在 `Proven`（清零）/ `DeliveryOnly` / `Miss`（按预算到顶 latch）上动，
   `Inconclusive` 既不花也不还 —— 与"本机拥塞两个方向都不表态"的既有契约对齐。
   否则一次本机出口打满，会把路径挣来的加宽撤掉，接下来 3 次超时去指控对端。
   新增测试 `inconclusive_rounds_neither_spend_nor_re_arm_the_excuse`。
3. 断言改为验性质而非轮次奇偶：首次 `Proven` 必须落在第 `FAST_PROBE_MISSES_TO_DEGRADE` 轮，
   并新增 `ProbeSim::max_budget`（任一轮实际用过的最宽预算）≥ 队列。

### 门禁状态（此前记录不实）
- `cargo fmt --all -- --check` 当时**不干净**，6 处未格式化（`Proven | Miss` 分支、`assert!` 换行等），已 `cargo fmt --all` 修好。
- `cargo clippy -p easytier-core -- -D warnings` 当时**失败**：`inject_self_delivered_nic_packet`
  在默认 feature 下 dead_code（唯一调用方 `gateway/magic_dns/packet.rs` 在 `proxy-packet` 之后），
  本机 ET Test Fast 用的是默认 feature，所以这道门必红。两处方法已加 `#[cfg(feature = "proxy-packet")]`。
  现在：`clippy -p easytier-core -- -D warnings` → exit 0；`check -p easytier-core --features proxy-packet` → exit 0。

  属原生构建环境问题，不是 lint。交给 CI 的 Linux 门禁或 `script\easytier-test.cmd fast`。

- 单向故障检测时间 **≈4.7s**，不是 6.2s：`Miss` 也把 `budget_floor` 减半，所以第 4/5 轮预算是
  600/300ms 而非 1200ms（0.63+0.93+1.53+0.93+0.63）。`docs/roadmap/live-next-hop.md` 的表格与结论已同步，

- 日志字段 `budget_floor_ms` → `next_budget_floor_ms`：该值在打印时**已是下一轮的** floor，
  与本轮 `budget_ms` 同名易误读。

### 教训
新增测试通过 ≠ 新增机制生效。凡是"加了一个参数/棘轮/闸门"的改动，必须有一条**消费该状态的用例**，
并用一次对照实验（把状态置为常量）确认它会变红。`assert!(excuse.spent)` 只证明字段被写过，
不证明它被读过。
