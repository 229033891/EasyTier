## 1. 背景与问题

当前节点 A 通过「子网代理 CIDR」宣告本机可代理的网段，对端 B 按 **IP/CIDR** 把流量导到 A。  
实际场景中，访问目标往往以 **域名** 出现，仅维护 IP 清单有以下痛点：

1. CDN / 动态解析导致 IP 常变，手工改 CIDR 成本高。
2. A、B 配置的 DNS 服务器即使相同，仍可能因 GeoDNS、EDNS Client Subnet、Anycast、轮询、缓存等得到 **不同答案**。
3. 若只在 A 解析并下发 CIDR，而 B 访问时再按本机 DNS 解析同名，目标 IP 可能不落在已通告 CIDR 内 → **无法命中代理**。
4. 部分域名不应查询第三方 DNS，而应使用 **固定的域名 → IP 清单**（类 hosts）。

结论：域名场景要稳定，必须保证 **「B 实际连出的 IP」与「A 通告的代理 CIDR」来自同一事实来源**，且 B **不能**对这类域名再独立递归查询。

---

## 2. 目标

1. 支持在代理节点（A）配置 **域名清单**，驱动子网代理。
2. 支持两类来源：
   - **静态映射**：直接定义 `域名 → IP 列表`，不查询第三方 DNS。
   - **动态解析**：仅配置域名，由 A 按指定/本机 DNS 解析并刷新。
3. 将解析/映射结果：
   - 合并进 A 的 `proxy_cidrs`（通常为 `/32` 或可聚合前缀）并经现有 Peer 路由通告；
   - **同一份** `域名 → IP` 下发给消费节点（B）做解析覆盖。
4. B 对这些域名只用下发结果建连，避免二次解析导致打不中。

非目标（首期不做）：

- 全系统无感 DNS 劫持（各 OS 钩子）可作为后续增强，不阻塞 MVP。
- 不替代 SOCKS5 / 出口节点等既有能力；可并存。

---

## 3. 不采纳的方案（及原因）

| 方案 | 原因 |
|------|------|
| 仅 A 解析并下发 CIDR，B 仍用系统 DNS 访问域名 | A/B 答案可能不一致 → 无法命中 |
| B 解析后推给 A，A 再下发 CIDR | 解析视角常错误；信任风险；B 仍可能二次解析；协议更重 |
| 假设「两边 DNS 配置相同则结果相同」 | Geo/ECS/Anycast/轮询下不成立 |

## 4. 推荐架构

### 4.1 数据流

```
A 配置:
  - 静态: name + ips[]
  - 动态: name + resolve=true (+ 可选 dns)

        ┌─────────────────────────┐
        │  A: Domain Proxy Engine │
        │  合并静态 + 动态解析结果 │
        └───────────┬─────────────┘
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
 更新 proxy_cidrs            生成「域名→IP」记录集
 （现有路由通告）              （同步给对端覆盖解析）
        │                        │
        └───────────┬────────────┘
                    ▼
              B: 路由命中 + 域名覆盖
           （不再对清单内域名做公共递归）
```

### 4.2 单一事实来源

- **权威视角固定在代理配置节点 A**（静态清单或 A 侧解析）。
- 下发给 B 的是 **答案记录**，不是「去问某个 DNS」的指令。
- 冲突规则建议：**静态优先于动态**；同一域名多来源时以配置顺序或显式优先级为准。

### 4.3 与现有组件关系

| 组件 | 作用 |
|------|------|
| `proxy_cidrs` / Peer 路由 | 继续承担 L3 导流；域名引擎只负责生成/更新 CIDR |
| MagicDNS / DNS 记录同步 | 优先复用或扩展，用于把 A 记录下发到 B |
| SOCKS5 / 出口节点 | 可选替代路径；应用层带域名时由 A 解析，不依赖本设计 |

### 4.4 MVP 前提（明确写进产品说明）

首期要求 B 使用节点提供的 DNS 覆盖路径（例如已启用 MagicDNS，或系统 DNS 指向本节点 DNS 服务）。  
未走覆盖路径时，行为与今日相同：仅 CIDR 生效，域名二次解析仍可能打不中。

## 5. 配置草案（示意，非最终字段）

```toml
# 静态：直接使用，不查询第三方 DNS
[[proxy_domains]]
name = "nas.lan"
ips = ["10.0.0.5", "10.0.0.6"]

# 动态：由 A 解析并刷新
[[proxy_domains]]
name = "cdn.example.com"
resolve = true
# dns = "udp://1.1.1.1:53"   # 可选；默认 A 本机 DNS
```

实现时需同步考虑：

- Web / GUI / CLI / 托管配置（`NetworkConfig`）字段与校验
- 数量上限、仅私网或前缀白名单（防误代理公网大段）
- IPv4 先做；AAAA / IPv6 后续

## 6. 分阶段计划

### Phase 0 — 文档（当前）

- 本文档立项；**不写业务代码**。

### Phase 1 — 静态映射 MVP（建议优先）

- A：`域名 → IP[]` 静态配置
- 自动合并进 `proxy_cidrs` 并通告
- 经 MagicDNS（或等价通道）把记录同步到 B
- GUI/Web 可编辑静态清单
- 文档说明 B 需启用 DNS 覆盖路径

**粗估**：约 1 周（熟悉仓库的 1 人）

### Phase 2 — 动态解析

- A 定时 / 按 TTL 解析
- 防抖、失败时保留上次成功结果
- 与静态合并、静态优先

**粗估**：在 Phase 1 基础上约 +1 周（合计 MVP 域名能力约 1～2 周；较稳可用约 2～3 周）

### Phase 3 — 增强（可选）

- 各平台更强 DNS 劫持 / Fake-IP，减少对「手动指 DNS」的依赖
- IPv6、更细策略与可观测性（当前生效映射表、最后解析时间/错误）

**粗估**：再加约 2～4 周

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| B 未使用覆盖 DNS | MVP 写清前提；UI 提示；后续 Phase 3 |
| 动态解析抖动 | TTL 下限、防抖合并更新「路由 + 记录」 |
| 误代理公网 | `/32` 为主、数量上限、可选仅私网 |
| 多记录 / CDN | 同步全部 A 记录；成对更新 CIDR 与覆盖 |
| 配置错误静态 IP | 校验、展示生效表、易回滚 |

---

## 8. 验收要点（实现时）

1. **静态**：A 配置 `nas.lan → 10.0.0.5` 后，B（走覆盖 DNS）解析得 `10.0.0.5`，且流量经 A 子网代理到达。
2. **故意制造 DNS 不一致**：B 本机公共 DNS 将同名解析到其它 IP 时，只要走覆盖路径，仍命中 A 下发的 IP。
3. **动态**（Phase 2）：A 侧解析变更后，在防抖窗口内 B 的覆盖记录与代理 CIDR 一致更新。
4. **未开覆盖**：行为可降级为「仅 CIDR」，不破坏现有纯 IP 子网代理。

## 10. 结论

- **可行**，宜复用子网代理通告 + DNS 记录下发，而不是让 B 独立解析。
- **静态映射**应作为第一刀；**动态解析**紧随其后。
- **当前状态：仅文档，暂缓开发。** 启动实现时以本文 Phase 1 为入口，并先确认开放问题 1～2。
