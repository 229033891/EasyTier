## 1. 背景与问题

部分网络环境会限制或干扰 **可识别的 P2P / VPN 隧道**（非常用端口、UDP 打洞、协议指纹、长连接特征等）。  
业界已有成熟思路：把隧道外层做成 **普通 HTTPS / Web 访问**，或降低被动指纹；EasyTier 目前仅有 `wss` / `quic` / `faketcp` 等传输，**没有**完整伪装产品档。

目标：在合法自建/自有域名与证书前提下，提供可选的「伪装传输」路径，使节点间（或经中继）流量更接近正常 Web，降低被策略误伤的概率。  
**不承诺**对抗所有主动探测或审查系统；文档与 UI 不得夸大。

---

## 2. 目标

1. **MVP**：推荐并产品化「中继 + `wss` + 443 + 合法证书 + 可选 path」部署范式（文档、模板、健康检查）。  
2. **增强**：可选 TLS 层伪装（证书策略、ALPN、尽量贴近浏览器 ClientHello）。  
3. **可选**：与现有 `faketcp` 等策略组合，用于 UDP 受限环境。  
4. 与打洞策略可切换：优先伪装中继，或「能打洞则打洞、失败回落伪装中继」。

非目标（首期）：

- 不实现完整第三方代理协议栈（Shadowsocks/VLESS 全兼容）作为主路径；可 **借鉴思路** 或 **桥接**，但 EasyTier 身份与路由语义保持独立。  
- 不做域前置（domain fronting）依赖（环境可用性不稳定）。  
- 不与「多链路加带宽」绑定；二者可独立启用。

## 3. 分层模型

```
┌─────────────────────────────────────────────┐
│ L3  EasyTier 数据面（PeerConn / 加密 / 路由） │
└─────────────────────┬───────────────────────┘
                      ▼
┌─────────────────────────────────────────────┐
│ L2  会话封装（WS 帧 / QUIC stream / …）        │
└─────────────────────┬───────────────────────┘
                      ▼
┌─────────────────────────────────────────────┐
│ L1  外观层（TLS 证书、SNI、ALPN、端口 443）   │  ← 伪装重点
└─────────────────────┬───────────────────────┘
                      ▼
┌─────────────────────────────────────────────┐
│ L0  IP 路径（直连 P2P / 中继下一跳）           │
└─────────────────────────────────────────────┘
```

硬规则：

- **伪装只保证 L1（及部分 L2）观感**；不改变 EasyTier 组网语义。  
- **权威网站内容不是必须**：MVP 可用「仅 TLS 终结 + WS upgrade」；增强期再考虑与真站同证书/同端口分流。  
- 帮助文案只描述 Current 已交付行为；Roadmap 能力落地前不得写入 i18n 承诺。

---

## 4. 推荐默认语义

| 问题 | 建议默认 |
|------|----------|
| 抗限连优先怎么走？ | **公网中继 + `wss://域名:443`**，合法证书 |
| 是否默认关闭打洞？ | 否；提供「偏好伪装中继」开关，失败再试其它 |
| TLS 证书 | 用户自备（ACME）；不做自签当「像公网网站」 |
| 路径 | 支持非 `/` path，降低简单扫描命中 |
| 与 bonding | 独立；伪装链路上仍可后续做多流（见 multi-link-bonding） |

## 5. 分阶段

### Phase A — 部署范式与可观测（优先，少改核心）

1. Ops/文档：中继节点 `wss` 监听、证书、防火墙、客户端 peer URL 模板。  
2. 状态面标明隧道 scheme、是否 TLS、是否经中继（避免用户误以为已「网站级伪装」）。  
3. 验收：按模板部署后，两节点经中继 `wss:443` 可组网。

### Phase B — 产品化「伪装传输档」

1. 配置预设：`transport_profile = plain | web_wss`（名称待定）。  
2. `web_wss`：默认倾向 443、要求 host/SNI、可选 path；UI 提示证书与 DNS。  
3. 打洞策略与 profile 联动（可选禁用 UDP 打洞以降低特征）。

### Phase C — TLS 指纹与同端口分流（可选）

1. 评估 uTLS / 固定浏览器指纹、ALPN（`http/1.1` / `h2`）策略。  
2. 同端口：TLS 后按 path 分流到静态站点 vs EasyTier WS（运维复杂度高，单独立项）。  
3. 明确不支持/不做的探测对抗范围。

### Phase D — 研究项（需再决策）

- 桥接外部成熟隧道（仅作外层 pipe），EasyTier 跑在内层。  
- REALITY 类「蹭真站」方案的合规与维护成本评估。  
- 与 `faketcp` 组合的推荐矩阵（按地区/运营商文档化，而非写死一套）。

---

## 6. 风险

| 风险 | 缓解 |
|------|------|
| 夸大「完全隐身」 | Status 保持 Draft；UI 只用 Current 措辞 |
| 证书/域名运维负担 | Phase A 先文档化；提供检查清单 |
| 主动探测（非 WS 则断） | Phase C 前书面接受；MVP 不承诺 |
| 法律与 ToS | 文档声明仅供合法组网与穿透；遵守当地法律与运营商规定 |
| 维护成本 | 优先复用现有 `wss`，避免首期自研完整代理生态 |

---

## 7. 验收要点（实现时）

1. Phase A：按文档仅用现有 `wss` 即可完成「中继 + 443」组网；状态可读。  
2. Phase B：一键/预设切换后，新节点默认走伪装档，无需手写冷门端口。  
3. Phase C（若做）：在约定测试环境中，被动指纹与「普通浏览器访问同 SNI」的差异有说明与基线对比。  
4. 关闭伪装档：行为回到 [`../current/tunnels-and-transport.md`](../current/tunnels-and-transport.md)。

---

## 8. 结论

- 成熟方案存在；EasyTier **可借鉴「TLS/Web 外观」**，不必首期重写整套代理协议。  
- **当前状态：仅文档立项。** 启动以 Phase A（部署范式）→ Phase B（产品预设）为序。  
- 与 bonding、出口导流分属不同问题，勿捆成一个大爆炸需求。
