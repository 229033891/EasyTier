## 1. 问题合并后长什么样

今天存在三条「看起来都能把流量弄出去」的能力，但职责交叉、文案夸大、失败不可见：

| 能力 | 用户直觉 | 实际负责层 |
|------|----------|------------|
| `exit_nodes` / `enable_exit_node` | 「配了出口，本机上网全走它」 | **仅 Peer 选路兜底**；不装系统默认路由 |
| `proxy_cidrs` 子网代理 | 「宣告网段，对端自动有路由」 | OSPF 通告 + TUN **系统路由**同步 |
| 域名访问目标 | 「填域名就能代理」 | 尚无；只有 IP/CIDR，且 B 侧 DNS 可能与 A 不一致 |

叠加后的真实痛点：

1. **出口配了却像没路由**：`exit_nodes` 不触发 TUN `0.0.0.0/0`，OS 流量进不来。
2. **路由删不干净 / 加不上还不重试**：`apply_route_changes` 失败仍改内存集合。
3. **域名代理若只下发 CIDR**：B 用自己的 DNS 解析，IP 对不上 → 打不中（域名草案已论证）。
4. **若有人宣告 `0.0.0.0/0`**：LPM 命中后 **整表跳过 `exit_nodes`**，且不打 `exit_node` 标志 → 排障困难。

必须用**一层模型**把「谁负责把包送进 EasyTier」和「进了之后交给谁」拆开，再把域名、CIDR、出口放进同一优先级。

## 2. 三层模型（统一抽象）

```
┌─────────────────────────────────────────────────────────────┐
│ L0  意图配置 Intent                                          │
│  - exit_nodes / enable_exit_node                             │
│  - proxy_cidrs（手工网段）                                    │
│  - proxy_domains（静态映射 / 动态解析）                        │
│  - manual_routes（可选：接管整张 TUN 路由表）                   │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ L1  权威编译 Compile（只在「配置归属节点」上发生）              │
│  - Domain Engine：域名 → IP[]（静态优先于动态）                │
│  - 合并生成「本节点宣告的 proxy CIDR 集」                      │
│  - 生成「域名 → IP 答案记录」（给对端覆盖解析，非「去问 DNS」） │
│  - 不在此层安装本机默认路由（默认路由见 L2 客户端策略）         │
└───────────────┬─────────────────────────────┬───────────────┘
                │ OSPF / Peer 通告             │ MagicDNS 等答案同步
                ▼                             ▼
┌──────────────────────────┐    ┌──────────────────────────────┐
│ L2  入口 Ingress（每台本机）│    │ L2' DNS 覆盖（消费节点）       │
│ TUN/OS 路由装卸载          │    │ 清单内域名只用下发答案         │
│ 来源 = 对端宣告 CIDR       │    │ 未走覆盖 → 降级为「仅 CIDR」   │
│      ∪ 本机 exit 默认路由  │    └──────────────────────────────┘
│      （若配置了 exit_nodes）│
│ manual_routes 开启则整表覆盖│
└───────────────┬────────────┘
                ▼  包进入 TUN
┌─────────────────────────────────────────────────────────────┐
│ L3  Peer 选路 Forward                                        │
│  固定优先级（见 §3），选出 dst_peer + 是否 exit_node 标志       │
│  再经 OSPF 下一跳（最短跳 / latency_first）                   │
└─────────────────────────────────────────────────────────────┘
```

**硬规则**：

- **L2 不管「选哪个出口 peer」**，只决定流量是否进入虚拟网。
- **L3 不管装不装系统路由**，只决定进网后的 peer 与标记。
- **域名绝不让消费端独立递归当权威**（沿用域名草案）；权威永远在配置了 `proxy_domains` 的代理节点。

## 3. L3 Peer 选路优先级（写死，产品与实现共用）

对 **IPv4 单播**（广播另议），进入 `send_msg_by_ip` 后：

| 次序 | 规则 | `is_exit_node` | 典型场景 |
|------|------|----------------|----------|
| 1 | 虚拟网 VIP 精确命中 | false | 点到点 |
| 2 | **Proxy CIDR LPM**（含手工 CIDR + 域名编译出的 `/32` 等） | false | 子网代理 / 域名代理 |
| 3 | `exit_nodes` **配置列表顺序**，第一个 VIP 可解析的 peer | **true** | 真正的「出口节点」路径 |
| 4 | （可选宿主）`local_exit_node_fallback` | true | OHOS 等 |

IPv6：VIP →（Public IPv6 gateway）→ Proxy LPM → `exit_nodes`；链路本地不进出口。

### 3.1 与「出口默认路由」的配合（结果导向默认语义）

**推荐产品语义（结果优先，选定如下，后续实现按此执行）：**

> 客户端配置了非空 `exit_nodes`，且 **未** 开启 `manual_routes`、且 **未** `no_tun` 时：  
> **本机 L2 自动拥有一条由 EasyTier 管理的 TUN 默认路由 `0.0.0.0/0`（IPv6 后续再定 `::/0`）**。  
> 清空 `exit_nodes` 时，**只卸载本机因出口而安装的那条默认路由**，不动对端宣告的其它 CIDR。

这样：

- 文案「本机上网流量走出口」与行为对齐 → **结果可感知**。
- 不强迫出口机向全网宣告 `0.0.0.0/0`（避免所有 peer 都被装上默认路由）。
- L3 仍走次序 3，带 `exit_node` 标志；出口机需 `enable_exit_node`。

**冲突时的行为（必须写进 UI/文档）：**

| 情况 | 行为 |
|------|------|
| 对端已宣告更具体 CIDR / 域名 `/32` | L3 次序 2 命中 → **不走 exit 列表**（正确：内网/域名代理优先） |
| 对端宣告了 `0.0.0.0/0` | L3 次序 2 命中 → **exit 列表被跳过**；流量走「子网代理默认路由」路径（无 `exit_node` 标志）。UI 警告：与本机 `exit_nodes` 语义冲突，建议只保留一种默认出口策略 |
| `manual_routes` 开启 | L2 整表由手动列表接管；**不自动加出口默认路由** |

### 3.2 为何不采用「出口机通告 0.0.0.0/0」作为主方案

- 会让**未配置出口列表的节点**也装上默认路由。
- LPM 命中后丢失 `exit_node` 标志与列表顺序语义。
- 多出口时只能靠 OSPF 跳数抢主，与「列表优先级」产品语义不一致。

保留为**高级/兼容手段**即可，不当默认。

## 4. 域名代理如何嵌进同一模型

完整细节仍以域名草案为准；本设计只钉死**与出口/路由的交界**。

### 4.1 归属

- `proxy_domains` 配置在 **代理节点 A**（网络实例级配置，与 `proxy_cidrs` 同级；Web 托管随实例下发）。
- A 上 Domain Engine 输出：
  1. 追加进 **A 宣告的 proxy CIDR**（默认 `/32`，可聚合）；
  2. **域名 → IP[] 答案记录** 同步到消费节点 B。

### 4.2 优先级（域名子系统内部）

1. 静态映射 > 动态解析  
2. 同一域名多条：配置顺序或显式 priority  
3. 编译进全局 proxy CIDR 后，在 L3 中与手工 `proxy_cidrs` **同一 LPM 表**，更长前缀胜出

### 4.3 与出口的关系

| 流量 | 期望路径 |
|------|----------|
| 访问「域名代理清单内」域名 | B 覆盖 DNS → `/32` LPM → A（次序 2） |
| 访问清单外公网 | 仅当 B 配了 `exit_nodes`（及本机默认路由）→ 出口 peer（次序 3） |
| 误把公网大段写进域名动态解析 | 用数量上限、默认 `/32`、可选仅私网缓解（域名草案 §7） |

域名代理 **不替代** 出口；二者分层：域名解决「打中哪台代理机的哪些 IP」，出口解决「剩余上网从哪出」。

### 4.4 MVP 前提（不变）

B 必须走 MagicDNS / 节点 DNS 覆盖；否则仅 CIDR 生效，二次解析可能打不中。

## 5. L2 系统路由：所有权、增删、可靠性

### 5.1 路由所有权标签（实现时必须有）

每条由 EasyTier 写入的 TUN 路由应带逻辑来源，便于对称卸载：

| owner | 来源 |
|-------|------|
| `peer_proxy` | 对端 OSPF 宣告的 proxy CIDR（含域名编译结果） |
| `local_exit_default` | 本机因 `exit_nodes` 非空而安装的 `0.0.0.0/0` |
| `manual` | `manual_routes` 整表 |

删除规则：**只删自己 owner 的条目**；禁止「集合差分数」误删他方路由。

### 5.2 失败语义（修现状缺陷）

当前 `apply_route_changes`：OS `add`/`remove` 失败仍更新内存集合 → 「装不上却以为装上了 / 删不掉却以为删了」。

统一改为：

1. **仅成功时**更新「已安装集合」；
2. 失败打 **warn**（含 ifname、cidr、owner、错误）；
3. 周期性或事件驱动 **reconcile 重试**（有上限与退避）；
4. 对外可观测：RPC/状态页可展示「期望路由 vs 已安装 vs 最后错误」（可与域名生效表同期做）。

### 5.3 性能与安全护栏

| 项 | 要求 |
|----|------|
| 默认路由进 TUN | 全流量用户态；仅 `exit_nodes` 非空时启用；UI 强提示带宽/断网风险 |
| metric | 平台相关：避免无脑抢死物理默认路由导致无法管理；实现阶段按 OS 定默认 metric 策略 |
| 出口机自环 | 出口机若自身也配了指向 TUN 的默认路由且 `enable_exit_node`，需文档禁止或检测告警 |
| 域名 `/32` 数量 | 上限 + 防抖，避免路由表抖动打满 |
| 热路径 | L3 保持 VIP + LPM；`exit_nodes` 仅 miss 时短列表扫描 |

## 6. 配置面（示意）

```toml
# —— 出口（客户端）——
exit_nodes = ["10.126.126.1"]   # 非空 → 本机自动管 TUN 默认路由（见 §3.1）

# —— 出口（服务端）——
# flags.enable_exit_node = true

# —— 手工子网代理 ——
proxy_networks = ["10.0.0.0/24"]

# —— 域名代理（仅代理节点 A）——
[[proxy_domains]]
name = "nas.lan"
ips = ["10.0.0.5"]              # 静态

[[proxy_domains]]
name = "cdn.example.com"
resolve = true                  # 动态；可选 dns =

# —— 高级：整表手动 ——
# routes = ["192.168.0.0/16"]  # 开启后接管 L2，不再自动加 exit 默认路由
```

GUI/Web：

- `exit_nodes` 旁注明：「将安装本机默认路由经虚拟网出站；与对端 `0.0.0.0/0` 代理冲突时以后者为准（LPM）。」
- `proxy_domains` 旁注明：「需对端启用 MagicDNS/覆盖 DNS。」
- 冲突检测：本机有 `exit_nodes` 且路由表中存在来自 peer 的 `0.0.0.0/0` → 警告。

## 7. 分阶段（实现顺序，仍先不写代码）

### Phase A — 出口结果可用 + 路由可靠（优先交付「能上网/能删路由」）

1. 修复 L2 增删失败记账与重试。  
2. 本机 `exit_nodes` ↔ `local_exit_default` 默认路由所有权。  
3. 文案/帮助与冲突提示。  
4. 基础测试：加出口装上默认路由；清空卸下；与 peer `10.0.0.0/24` 并存不误删。

### Phase B — 域名静态映射 MVP

按域名草案 Phase 1：静态 `域名→IP` → 合并宣告 + MagicDNS 下发。

### Phase C — 域名动态解析

TTL/防抖、失败保留上次成功、与静态合并。

### Phase D — 可观测与增强

期望/已安装路由表、域名生效表、可选 Fake-IP / 更强 DNS 劫持、IPv6 默认路由策略。

## 8. 验收场景（跨出口 + 域名）

1. **仅出口**：B 配 `exit_nodes=A`，A 开 `enable_exit_node`，B 出现 TUN 默认路由；访问公网 IP 经 A 出网；清空 `exit_nodes` 后默认路由消失。  
2. **出口 + 内网 CIDR**：A 另宣告 `10.0.0.0/24`；B 访问 `10.0.0.5` 走 LPM 到 A（非 exit 标志）；访问 `8.8.8.8` 走 exit 标志。  
3. **域名静态**：A 配 `nas.lan→10.0.0.5`；B 走覆盖 DNS 得同一 IP，流量经子网代理到 A。  
4. **域名 + 出口**：清单内域名走 A 代理；清单外上网走 `exit_nodes`。  
5. **冲突**：某 peer 宣告 `0.0.0.0/0` 时，B 若仍配 `exit_nodes`，UI 警告；实际按 LPM 走代理默认路由。  
6. **删路由**：对端撤销 CIDR 或本机清空出口后，对应 owner 的路由在重试后最终卸载。

---

## 9. 明确不做什么（首期）

- 不把「出口」默认做成全网通告 `0.0.0.0/0`。  
- 不让 B 对域名代理清单做权威递归。  
- 不用 ACL「按域名字符串」替代「按解析后 IP」（ACL 仍跟 IP；域名只影响如何得到 IP）。  
- 不在未开覆盖 DNS 时承诺域名代理 100% 命中。

## 10. 开放问题（实现前只需拍板少数几项）

| # | 问题 | 建议默认（可改） |
|---|------|------------------|
| 1 | IPv6 是否随 `exit_nodes` 自动装 `::/0` | Phase A 只做 v4；v6 单独立项 |
| 2 | Windows/macOS/Android 默认路由 metric | 实现时按平台表驱动；文档写「可能需管理员权限」 |
| 3 | `proxy_domains` 挂网络实例还是节点全局 | **网络实例**（与现有 `proxy_cidrs` 一致，便于 Web 托管） |
| 4 | 多节点对同一域名做代理 | LPM + OSPF path_len；同前缀多发布者与今日 CIDR 相同 |
| 5 | 域名条目是否允许 mapped CIDR | MVP 不做；静态 IP 即真实目标 |

## 11. 结论（给「无法决定、只要结果」的默认答案）

1. **入口**：谁配了 `exit_nodes`，谁的本机自动管默认路由（结果可见、可删）。  
2. **选路**：VIP → 代理 CIDR/域名 `/32`（LPM）→ `exit_nodes` 列表 → fallback。  
3. **域名**：只在代理节点做权威，CIDR + 答案记录成对下发；与出口分层并存。  
4. **可靠**：路由按 owner 对称装卸；失败不瞎记账，要重试、要可观测。  
5. **实现顺序**：先 Phase A（出口+路由可靠），再域名 Phase B/C。

本文选定上述默认语义后，**仍暂不实现代码**；启动开发时以 Phase A 为第一刀，并同步改帮助文案与冲突提示。
