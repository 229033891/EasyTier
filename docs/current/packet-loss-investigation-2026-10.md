## 2. 复现方法

```powershell
# 内层：经 ET 隧道
ping -n 240 -w 1000 10.10.10.51

# 外层：同一时刻并发，用于分离「隧道内」与「物理出口」
$a = Start-Job { ping -n 150 -w 1000 10.10.10.51 }
$b = Start-Job { ping -n 150 -w 1000 43.154.13.211 }   # et.scmec.vip 公网服务器
Wait-Job $a,$b; Receive-Job $a; Receive-Job $b

# ET 侧同步取证（日志为 UTC，warn 级）
Copy-Item "$env:LOCALAPPDATA\com.kkrainbow.easytier\logs\easytier.log" .\et.log -Force

# 路由归属
Find-NetRoute -RemoteIPAddress 43.154.13.211
Get-NetRoute -InterfaceAlias et -AddressFamily IPv4 | Where-Object Protocol -eq NetMgmt
```

> **方法学要点**：日志时间戳是 **UTC**，`+8` 才是本地时间；换算错会导致所有时间对齐失效。

## 4. 已证伪的假设

### 4.1 「是 ET 在做网络检查 / 路径切换造成的」——**证伪**

Run A 中 ET 全程静止（唯一日志是 wireguard 定时器），内层仍出现 0.4% 丢包与 413/234/72ms 尖峰。
Run C 中 ET 同样零日志，仍出现 524/194/114ms 尖峰。
→ **时延尖峰与 ET 的控制面动作无因果关系。**

### 4.2 「残留 2.1% 丢包是 bond / conn_select 切出口造成的」——**证伪**

Run B/C 的两个窗口内 `peer_link_replica_fill_max = 1`、无 bond 成员变动、ET 无任何选路日志，丢包仍出现（Run A）/ 不出现（Run B/C）——**与 ET 侧行为无相关性**。

### 4.3 「是底层链路的稳定劣化」——**部分证伪**

Run B 内层 150 包 **0% 丢包、max 24ms**；Run A/C 同样目标却出现 400–500ms 尖峰。同一路径在数分钟内从「完全平稳」变成「毛刺频发」，**不符合稳定劣化**，更符合**瞬时排队**。

### 4.4 「是 Clash 的 gvisor TUN 造成的」——**部分证伪**

关掉 TUN 后内层尖峰**没有消失，反而出现更大的 524ms**。
→ TUN 不是内层尖峰的原因（但确实影响外层，见 §5）。

## 5. 已确认：两个 VPN 双向互抢路由

这是本次调查最确定的结构性问题，**双向都被劫持**。

### 5.1 方向一：ET 外层流量被 Clash TUN 接管

Clash 运行时配置：`tun.enable: true`、`stack: gvisor`、`auto-route: true`、`dns-hijack: any:53`，**全文无 `route-exclude-address`**。

```
0.0.0.0/0  via 198.18.0.2   (Meta / mihomo TUN)  metric 0     ← 胜出
0.0.0.0/0  via 192.168.10.1 (Ethernet0)         metric 256
```

`Find-NetRoute` 实测：

| 目标 | 出口 | 命中路由 |
|---|---|---|
| `43.154.13.211`（et.scmec.vip） | `Meta` | `0.0.0.0/0` metric 0 |
| `124.222.29.94`（对端公网端点） | `Meta` | `0.0.0.0/0` metric 0 |

**后果**：ET 所有外层流量穿过 mihomo 的 **gvisor 用户态协议栈**。
**可观测影响**：走 TUN 的那条路实测 **2% 丢包**；切回物理网卡后 **0%**（样本仅 3 个包，`p≈0.05`，属趋势而非确证）。

### 5.2 方向二：Clash 代理服务器的流量被 ET 隧道接管

`et` 网卡上有 **23 条 `Protocol=NetMgmt` / metric 9000 / on-link** 路由，由 ET 为**对端发布的代理子网**而安装：

```
103.21.244.0/22   103.22.200.0/22   103.31.4.0/22
104.16.0.0/13     104.24.0.0/14     108.162.192.0/18
131.0.72.0/22     141.101.64.0/18   152.65.228.35/32
152.65.234.23/32  162.158.0.0/15    173.245.48.0/20
188.114.96.0/20   190.93.240.0/20   197.234.240.0/22
198.41.128.0/17   20.27.177.113/32  20.205.243.166/32
172.16.0.0/16     172.18.0.0/16     172.25.0.0/24
172.64.0.0/13     192.168.8.0/22
```

`Find-NetRoute 104.19.32.86`（本机 Clash 正在使用的代理节点）→ **出口 `et`，命中 `104.16.0.0/13`**。

**后果**：Clash 连接自己代理服务器的包被送进 ET 隧道，从对端节点出网；ET 的稳定性与 Clash 的稳定性互相耦合。
**源头**：某个 ET 节点的 `proxy_networks` / `proxy_cidrs` 发布了一整份代理 IP 列表。**这是唯一源头，清掉它比在 Clash 侧加排除更重要。**
**注**：`192.168.8.0/22` 覆盖 192.168.8–11，但本机 LAN `192.168.10.0/24` 更长故未受影响；其余私网段（`172.16/16` 等）会被 ET 隧道吃掉。

## 6. 已确认的 ET 侧缺陷

### 6.1 同 peer 多条 conn 被成簇拆掉（放大器，非起因）

`easytier.log`（warn 级，本地时间）：

| 时刻 | 事件 |
|---|---|
| 07:53:43 / 07:53:55 | 同 peer 两次拆连，间隔 12s |
| 11:26:55 / 11:30:27 / 11:30:31 | 三次 |
| 11:49:57 / 11:50:02 | 两次 |
| 12:04:15 / 12:04:16 / 12:04:22 | **7 秒内三次** |
| 12:23:39 / 12:23:44 | 两次 |
| **13:43:10 / 18 / 23 / 29** | **peer 2752719068 的 4 条 conn 在 19 秒内全被拆**，`loss_rate_1` 0.10→0.14 递增 |

全天 20 次 ping 触发的拆连，被拆 conn 的 `loss_rate_1` 在 **0.05–0.45**；peer `2365013564` 一天内 **81 次** conn 关闭。

`loss_rate_1` 递增说明**雪崩**：一条断 → 其流量压到剩余 conn → 剩余 conn 劣化 → 再断。
**ET 缺少「同一 peer 保留最后一条可用 conn」的保护**。这是 P1.5「抖动宽限」的具体表现（见审计文档 §8 P1）。

### 6.2 `find_interface_index("et")` 失败导致 socket 创建直接失败（**与网络无关的代码缺陷**）

```
easytier::arch::windows: Failed to find interface index for et      × 202
```

按分钟聚类：09:36 / 10:23 / 11:21 / 11:35 / 12:17 / 12:25 / 12:29 / 12:31，**每波约 32 次**。

失败传播链（**每一环都用 `?` 直接返回错误**）：

```
arch/windows.rs:83   find_interface_index()            → Err(NotFound)
arch/windows.rs:100  set_ip_unicast_if()               → Err          (设 IP_UNICAST_IF 失败)
arch/windows.rs:137  setup_socket_for_win()            → Err          (L157 `?`)
tunnel/common.rs:68  setup_socket2_ext()               → TunnelError  (L79 `?`)
```

**后果**：`find_interface_index` 失败的那一刻，**所有需要把出口网卡钉在 `et` 上的隧道/打洞 socket 全部创建失败**。
`find_interface_index` 用 `network_interface::NetworkInterface::show()` 按名字匹配硬编码的 `dev_name`，在适配器被重建/枚举异常时会失配，且**失配被当作致命错误**。

> **2026-10-18 已修**：P1（绑定失败降级为「不绑网卡」+ WARN）/ P2a·P2b（该路径日志 ERROR→WARN）/ P3a（`wait_interface_show` 加 30s 超时）/ P3b（路由 reconcile 整批就绪门控，不再逐个失败 32 次）。根因、修复与待验证项见 [`windows-wintun-interface-missing.md`](./windows-wintun-interface-missing.md)（真机复现仍待做）。

### 6.3 黑洞期 ET 无法自愈，只能等拆连链（既有结论，此处补证据）

PingInfoView 报告中 `12:57:22–12:58:30` 连续 27 次失败（~71s），DEV 日志在 **`12:57:43`** 出现
`too many consecutive pingpong failures, closing the connection … peer 2752719068` —— 落在黑洞正中，
`12:58:33` 恢复。黑洞起点（12:57:22）早于 ET 察觉（12:57:43）21s，**与「S1b 把发现前的等待从 32s 压到 10s」之后的预期量级一致**（注意：该次仍跑在默认 32s 的旧构建上）。

## 7. 未定性的部分

### 7.1 内层 200–500ms 尖峰的落点

形态是**瞬时排队**（3 个尖峰集中在 18 秒内，其余时间完全平稳），候选落点：

- home-pc 的上行链路 / 其 NAT 的缓冲区；
- ET 隧道自身（若该 conn 经中继，则中继节点的排队）；
- 对端主机自身的调度延迟。

**取证方法（必须双侧同时做）**：在 home-pc 上同一时刻跑
`ping -n 300 -w 1000 10.10.10.101`（内层）与 `ping -n 300 -w 1000 223.5.5.5`（它自己的公网出口），
对齐时间戳后判定尖峰是否共现。

### 7.2 PingInfoView 报告里的 0ms

报告 268 行中 **111 行为 0ms**、125 行为 15/16ms、另有 203/203/297ms，并在 `12:59` 前后从 15/16ms **永久切换**为 0ms。

从一台**非 DEV** 的机器 ping `10.10.10.101` 得到 `<1ms` 回复，物理上只可能来自本机协议栈。
用户已确认网内 VIP 分配唯一，因此**该现象尚未解释**。待验证项：
报告生成的那台机器上是否存在本地代理/TUN 拦截，或残留的 `.101` 地址。

## 10. GUI 显示连通、丢包 0%，Ping 却不通（2026-10-17 16:58–17:37）

PingInfoView（超时 500ms、重复间隔 **2 秒**）对 `10.10.10.101`、`10.10.10.101:3389`、`10.10.10.25` 一轮累计约 **70 次失败 + 十余次成功**，三个地址计数相同。`223.5.5.5` 同期几乎全成功。70 × 2s ≈ **140 秒**空窗，不是每个 Ping 重试 70 次，也不是每条新 TCP 都在重建 VPN。本机 `easytier.log` 在 17:14 之后没有与这些探测逐条对应的拆连或打洞。

同一时刻节点表把这些 peer 画成直连，丢包率 0%。两套数字看的不是一件事。

### 10.1 界面上的丢包率是保活，不是 Ping

节点表的丢包率来自 `PeerConnPinger` 在**这条 PeerConn** 上的保活窗口（`peer_conn_ping.rs` 把 0/1 记入 `WindowLatency`，再写入 `loss_rate_stats`）。有 conn 就显示连通。protobuf 省略 0 值时，前端 `lossRate()` 把缺失当成 0%（`statusDisplay.ts`）。

因此保活还在成功时，行上就是「直连、0%」。用户 ICMP / 对 `:3389` 的 TCP 探测不进入这个窗口。

> **2026-10-17 补**：这一条已被 Phase F 部分修复——快速活性探测（≈1.9s 判定不往返）会把结果写进同一个丢包率，所以**静默黑洞期间状态面不再显示 0%**。但它仍然**不是**用户 ICMP 的丢包率：那是数据面路径的可达性，两套数字依旧不是一回事。见 [`../roadmap/live-next-hop.md`](../roadmap/live-next-hop.md) §5.6。

### 10.2 数据包走延迟优先的下一跳，可以和这行直连不是同一条

`flags.latency_first` 默认 `true`（本机配置未覆盖）。从 TUN 出去的包在 `peer_manager.rs` 上打 `latency_first`，`get_gateway_peer_id` 查的是 **LeastCost** 路由表，不是节点表里那条正在画 RTT 的直连。

边权来自 peer-center 的 `DirectConnectedPeerInfo.latency_ms`。这个字段现在装的是质量分换算的整数代价（`ospf_edge_cost_from_score`：`score * 1000`，再 `clamp(1, …)`），名字仍叫 `latency_ms`。**注意：这是等价量纲的推广，不是把时延压缩掉**——`score = 1.0·rtt_s + 4.0·loss + 1.0·jitter_s`，所以 `cost` 就是「毫秒当量 + 丢包/抖动加权」；13ms 的直连仍然是代价 13。代价下限 1 只影响亚毫秒的同网段边。

所以表里「两跳代价 2」= 两跳各 <0.5ms，**这条中继腿当时确实比 13ms 直连更快，本次选路本身是对的**。真正的问题在下一小节：那条"快"的腿已经死了，但拓扑还在广告它。

DEV 上 `easytier-cli -p 127.0.0.1:15999 route`：

| 时刻 | 目标 | 最少跳 | 延迟优先 |
|---|---|---|---|
| 约 17:08 | home-pc `10.10.10.51` | 直连，路径代价 13 | **经 shdx，2 跳，路径代价 2** |
| 约 17:08 | DB `10.10.10.20` | 直连，路径代价 8 | 经 shdx，2 跳，路径代价 7 |
| 17:37 | home-pc | 直连，13 | 已回到直连，13 |
| 17:37 | DB | 直连，8 | **仍经 shdx，2 跳，代价 7** |

17:08 的 home-pc 就是「直连保活 13ms、丢包 0%」和「数据包被交给 shdx」同时成立。延迟优先之后可以自己切回来（17:37 的 home-pc），所以这是选路结果，不是网卡坏了。DB 这一行说明分叉仍在。

### 10.3 选中的下一跳发不出去时，包被丢掉，界面不变

`send_msg_internal`（`peer_manager.rs`）拿到 OSPF 下一跳后，若该 peer 没有活连接，返回 `RouteError(None)`，日志是 `cannot send msg to peer through gateway`。它不改试下一条还有活连接的路。`get_gateway_peer_id` 在最少跳策略下只要 `has_peer`（条目还在）就把目标自己当下一跳，不要求 `has_peer_with_live_conn`。

保活包是在已有的 PeerConn 上直接 ping，不走这次转发。所以直连行继续 0%，发往虚拟 IP 的 Ping 连续超时。

**责任在哪一跳**：本机这一跳的 conn 是**活的**（所以 §10.2 的选路坚持走 shdx），死掉的是 **shdx → home-pc** 那一跳，包在 shdx 那边被丢弃。本机对这件事**没有任何感知通道**——这就是「140 秒空窗」与「界面显示直连、丢包 0%」能同时成立的原因。也因此，任何只在本机侧加强下一跳筛选的改法都修不了它（见 [`../roadmap/live-next-hop.md`](../roadmap/live-next-hop.md) Phase F：快速活性探测 + 度量驱动降级）。

死记录要等多久才从拓扑里消失，决定空窗长度：保活最多隔 10 秒才探测，连续失败 10 次才拆（失败后单次仍等 2 秒，约 20–30 秒）；不可达节点的路由信息再保留 90 秒（`REMOVE_UNREACHABLE_PEER_INFO_AFTER`），清扫周期 60 秒（`clear_expired_peer`）。合计约 2–2.5 分钟，对应间隔 2 秒的 60–75 次失败。

旁证：peer `3230708021` 在 16:07:47 因保活失败被拆（`loss_rate_1 = 0.77`），OSPF 同步路由直到 **16:53:24** 才 `remove_peer`。中间 DEV 对该 peer 有 7512 条转发失败 / 转发跳数超过 7 被丢的日志。它不在 17:37 的 9 个在线节点里。

### 10.4 这次不修什么

- 不把 90 秒 / 60 秒改小当作修复。清扫变勤仍有空窗，而且会把刚抖动的节点提前忘掉。
- 不按每个 Ping 去重建隧道。隧道在空窗前后都在，断的是数据面的下一跳。

转发规则见 [`../roadmap/live-next-hop.md`](../roadmap/live-next-hop.md)。该文的目标是「只从已建立、且在通往目的路径上的链路转发」，但**首版实现（`choose_sendable_gateway` + 兜底 relay）经代码复核不被接受**：它只校验「有活连接」，不校验「通往目的」，因此会引入跨节点环路，且修不到本节的故障（DEV 侧 shdx 那条 conn 是活的，改后照样选它）。详见该文 §4。拓扑清扫保持原样。

本节只回答「黑洞期间为什么 GUI 说通、Ping 不通」。真正的修法（快速活性探测 + 度量驱动降级 = 该文 Phase F；OSPF 备份下一跳 / LFA = Phase B/D）见该文 §5、§6。

### 12.4 「ET 毛刺」结论的自我推翻（关键教训）

#### 12.4.1 曾经测到什么

19:10 用 200 ms 粒度双路径（ET + TS + CTL 公网对照）跑 10 分钟，得到：

| 路径 | p50 | p90 | p99 | max | 尖峰 | **单独尖峰** |
|---|---|---|---|---|---|---|
| ET | 11.6 | 12.7 | **30.3** | **708.3** | 13 | **5** |
| TS | 12.0 | 13.4 | 29.7 | 254.8 | 8 | **0** |
| CTL | 10.0 | 11.0 | 13.6 | 253.7 | 8 | **0** |

当时据此判定：**「ET 有 5 次独有尖峰，TS/CTL 为 0，jitter 高 35%，p99 高」** —— 即 ET 存在独立的尾部缺陷。

#### 12.4.2 80 分钟后又测到什么

20:00 用 100 ms 粒度跑 20 分钟，**90 次尖峰 / 11032 样本（0.82%）**，且 93%（84 次）**成簇**出现，每簇持续 7.9–34.5 秒：

| 时段 | 状态 | 尖峰 |
|---|---|---|
| 20:00:40–20:02:40 | 干净 | 0 |
| 20:02:40–20:13:50 | 上传进行中 | 5 |
| 20:13:53–20:20:40 | **上传加剧**（经 `10.10.10.25`/shdx 上传） | **85（成簇）** |

上传停止后（20:25）5 分钟复测：**21 次 / 1406 样本 = 1.49%**，占比反而比上传期间（0.82%）更高 —— 说明「90 次全是上传造成」这个假设也不成立。

#### 12.4.3 真相：`Thread.Sleep` 定时抖动污染了 RTT

20:31 用 50 ms 粒度（`Thread.Sleep` 控间隔）复现出的形态：

```
20:31:51.207  seq=591   271.3 ms   ← 慢
20:31:51.217  seq=592    10.1 ms   ← 快（只隔 10 ms！）
20:31:51.538  seq=593   267.2 ms
20:31:51.548  seq=594     9.7 ms
20:31:51.828  seq=595   238.2 ms
20:31:51.841  seq=596    12.3 ms
```

**严格快-慢交替，慢样本集中在 200–283 ms 这一狭窄区间。**

诊断：慢样本的 RTT 实际上包含「等待下一个可读时机」的时间，而相邻 10 ms 的快样本才是真实往返。即 **回包早就到了，是测量程序自己阻塞**。

根因在测量脚本：

```powershell
# 错误写法
$sw = Stopwatch::StartNew()          # ← 计时器在 Send 之前启动
$sock.Send(...)
...
$rem = 50 - $w.Elapsed.TotalMilliseconds
[System.Threading.Thread]::Sleep([int]$rem)   # ← 实际可能睡 50–300 ms
```

`Thread.Sleep` 受 Windows 默认定时器精度（约 15.6 ms）与非实时线程优先级影响，**在 PowerShell 宿主上抖动可达数百毫秒**。把这个抖动算进 RTT，就产生了 200–700 ms 的「尖峰」。

#### 12.4.4 修正后的测量：忙等待

```powershell
# 正确写法
while($sw0.Elapsed.TotalMilliseconds -lt $next) { }   # 忙等待，精度 <1 ms
$next += 50
$sock.Send(...)
$w = Stopwatch::StartNew()                            # ← 计时器在 Send 之后
```

同一路径、同样 90 秒的结果对比：

| | 旧（`Sleep`） | **新（忙等待）** | TS 基线 |
|---|---|---|---|
| n | 1406 | 1801 | 1406 |
| p50 | 11.9 | **11.3** | 11.4 |
| p90 | 12.9 | **12.0** | 12.4 |
| **p99** | **121.9** | **15.7** | 17.0 |
| ≥60 ms 占比 | **1.49 %** | **0.50 %** | 0.57 % |

**`p99` 从 121.9 → 15.7 ms，尾部尖峰比例从 1.49% → 0.50%，与 TS 基线（0.57%）完全持平。**

#### 12.4.5 结论

| 之前记录的说法 | 状态 |
|---|---|
| ET 有 5 次独有尖峰（708/233/169/107/128 ms） | **撤回**，脚本抖动 |
| ET jitter 3.1 vs TS 2.3（高 35%） | **撤回**，同一原因 |
| ET p99 121.9 vs TS 17.0（差 7 倍） | **撤回**，忙等待版本已证伪 |
| 「8/13 主机卡顿 + 5/13 ET 问题」的归因 | **撤回**，两者都是测量噪声 |
| 上传期间 90 次尖峰成簇 | **保留**，真实带宽饱和效应（任何隧道都同样受影响） |
| ET 吞吐 6.06 vs TS 6.33 MB/s | **保留**，TCP 大包传输，不受计时抖动影响 |
| 中继 4.83 → 直连 6.06 MB/s | **保留**，有包级证据 |

**最终结论：ET 与 TS 在这条直连路径上延迟完全同级。**

| 指标 | ET | TS | 差距 |
|---|---|---|---|
| p50 | 11.3 | 11.4 | 相同 |
| p90 | 12.0 | 12.4 | ET 略好 |
| p99 | 15.7 | 17.0 | ET 略好 |
| ≥60 ms 占比 | 0.50 % | 0.57 % | 相同 |

### 12.5 方法论教训（务必遵守）

1. **亚百毫秒级 RTT 测量禁止使用 `Thread.Sleep` / `Start-Sleep` 控节奏。** 两者在 PowerShell 上有数十到数百毫秒抖动，会被计入 RTT 而伪造出「尖峰」。改用忙等待 + `Stopwatch` 对齐。
2. **计时器必须在 `Send` 之后启动**，否则会把发送前的调度延迟算进往返时间。
3. **单路径测量不可归因。** 必须同时跑对照路径（另一条隧道 + 裸公网 TCP）才能区分「隧道问题」与「主机/线路问题」。19:10 那轮正是因为有三路径对照，才发现 8/13 尖峰是三路径同时发生（主机级）。
4. **包级统计必须按端口/五元组过滤。** 首次统计把整个 `192.168.10.96` 的流量都算成「中继腿」，结果把 RDP（`3389`，9912 包）和 SSDP 组播（`1900`）全部计入，虚报出「中继腿 49,032 包 / 10.3 MB」的假象。ET 业务流应只认 `11010/11011`。
5. **`pktmon` 的时间戳是 7 位小数**（`.439615400`），`ParseExact` 用 `'yyyy-MM-dd HH:mm:ss.fff'` 会抛 `FormatException`；应改用 `TryParse` + `InvariantCulture`。
6. **日志级别 `warn` 下静默不等于「无事件」。** 两台机器的 `easytier.log` 在测试时段（18:17 之后）均无新增，只能说明没产生 warn 级事件，不能据此推断数据面无异常。对照：`easytier.log.2` 有 12.8 MB，证明该级别日志是能大量产生的。
